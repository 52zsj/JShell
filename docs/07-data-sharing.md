# 07 · 数据与配置共享（多设备同步）可行性分析

状态：**方案分析，未实现**
适用：JShell 0.5.x
日期：2026-10-27

---

## 1. 结论先行

**推荐路线：客户端加密的「同步包」+ 自带存储（BYOS）适配器；不做账号体系、不自建云端。**

理由是 JShell 的现有定位（纯本地、无账号、默认不上报任何数据）与「账号 + 云」路线天然冲突，
而配置同步这件事本身不需要后端——只需要一个用户自己信任的「放文件的地方」。

落地优先级：

| 阶段 | 内容 | 新依赖 | 估时 |
| --- | --- | --- | --- |
| P0 | 加密同步包（单文件）+ 完善导出/导入 | 无（`node:crypto`） | 1~2 天 |
| P1 | **文件夹适配器**（iCloud Drive / OneDrive / Dropbox / 任意目录）+ 自动合并 | 无（`fs.watch`） | 3~5 天 |
| P2 | **SFTP 适配器**（拿自己一台服务器当同步盘） | 无（`ssh2` 已有） | 2~3 天 |
| P3 | WebDAV（坚果云 / Nextcloud / NAS） | 可选小库 | 2~3 天 |
| P3 | GitHub Gist / Gitee 代码片段 | 无 | 2~3 天 |

**不建议**：自建 JShell 云账号体系（要承担后端、运维、账号、合规成本，且直接违背「无账号、不上报」的产品承诺）。

> 一句话：**把「存哪儿」做成可插拔的适配器，把「安不安全」交给客户端加密。**
> iCloud / OneDrive / Dropbox 只是「文件夹适配器」的三种落点，不需要各写一套。

## 2. JShell 现在存了什么

| 文件 | 内容 | 敏感性 | 适合同步 | 原因 |
| --- | --- | --- | --- | --- |
| `data/state.json` · hosts | 名称、地址、端口、用户名、认证方式、私钥路径、分组、颜色 | **高** | 可（加密） | 等于一张内网资产地图 |
| `data/state.json` · settings | 主题、字号、快捷键、显示偏好 | 低 | 部分 | 部分项与设备强相关（见 §8） |
| `data/state.json` · snippets | 命令片段 | 中 | 可（加密） | 片段里常含内部命令、甚至口令字面量 |
| `data/state.json` · tunnels | 端口转发配置 | 中 | 可（加密） | 暴露内网服务拓扑 |
| `data/state.json` · knownHosts | 主机公钥指纹 | **高** | 可选（默认关） | 这是信任锚，被污染等于 MITM |
| `data/secrets.json` | 密码、私钥口令 | **极高** | 默认否 | 见下方「关键约束」 |
| `data/layout.json` | 标签 / 分屏结构 | 低 | 否 | 设备相关，同步后反而错乱 |
| `data/window.json` | 窗口位置尺寸 | 低 | 否 | 设备相关 |
| `logs/` | 运行日志 | 中 | 否 | 可能含主机名 / IP |

### 关键约束：凭据是「机器绑定」的

`secrets.json` 用 Electron `safeStorage` 加密，底层是 **macOS Keychain / Windows DPAPI / Linux 密钥环**。
这类密文与「当前设备的当前用户」绑定，**换一台机器无法解密**（代码里 `unseal` 失败即视为未保存）。

所以：

- ❌ 不能把整个 `data/` 目录丢进网盘 —— 密码解不开、`layout` 会串、明文 `hosts` 会泄露；
- ✅ 必须导出成一个**独立的、可控内容**的同步包；
- ✅ 密码如果要跨设备，只能在同步包里**再加密一次**（端到端），到目标设备后再用本机 Keychain 重新封装。

## 3. 设计约束

1. **不能整目录同步**（机器绑定 + 明文泄露 + 设备相关文件）。
2. **无账号、无后端**（保持现有定位）。
3. **跨 macOS / Windows**（Linux 次要）。
4. **服务端零信任**：云盘 / Gist / WebDAV 都当作「不可信存储」。
5. **凭据可选同步**，且必须端到端加密。
6. **私钥路径跨设备不一致**，需要单独处理。
7. **现有 `importConfig` 不能直接复用**：它会重新生成 id，且**丢掉了 `proxyJump` 字段**（跳板机关系会断）。

## 5. 逐方案分析

### 5.1 文件夹同步（iCloud Drive / OneDrive / Dropbox / 任意目录）——**首选**

- **做法**：用户选一个目录，App 在里面读写 `jshell-sync.v1.json`（加密包），监听文件变化自动合并。
- **优点**：零后端；三家网盘在系统里都只是「普通文件夹」；用户自己掌控存放位置；离线可用；换网盘零改动。
- **缺点**：iCloud Drive 在 Windows 上依赖 iCloud for Windows，写入可能延迟，体验一般（Windows 建议 OneDrive / Dropbox / SFTP）；网盘冲突时可能生成「副本」文件，需要我们能识别。
- **安全（重点）**：**不要依赖 iCloud 自身加密**。iCloud Drive 默认只保证「传输 + 静态加密」，密钥在 Apple 手里，
  只有开启「高级数据保护（ADP）」才是端到端。所以必须**自己做 E2E 加密**，让网盘只看到密文。
- **结论**：可行，性价比最高，作为第一个适配器。

### 5.2 GitHub Gist / Gitee 代码片段

- **做法**：用户填 token，App 读写一个（私有）片段文件。
- **优点**：天然版本历史；跨平台；API 极简（一个 HTTP PUT/GET）。
- **缺点**：
  - GitHub 的「secret gist」只是**不被列出**，**拿到 URL 就能读**，不是真正私有 → **必须先加密**；
  - GitHub 在中国大陆访问不稳定；Gitee 的片段/API 配额与权限需实测；
  - token 通常带 `gist` 权限，泄露面大 → 只能存 `safeStorage`，绝不写日志；
  - 只能整文件覆盖，没有字段级合并。
- **结论**：适合作为 P3 的「极客选项」，不适合做默认。

### 5.3 Git 仓库

- **做法**：调用本机 `git`，或不引入依赖用 `isomorphic-git`（会新增依赖 + 体积）。
- **优点**：版本化、diff、回滚；和运维/`dotfiles` 习惯契合；私有仓库权限成熟。
- **缺点**：依赖 git 二进制；要处理 merge 冲突；对非开发者门槛高；凭据管理复杂。
- **结论**：进阶用户向，优先级低于「文件夹」与「SFTP」。

### 5.4 WebDAV

- **做法**：`PUT/GET` + `PROPFIND`，Basic/Digest 认证。
- **优点**：坚果云、Nextcloud、群晖、多数 NAS 都支持；国内可用性好；协议简单。
- **缺点**：各家实现细节不一；并发/大文件一般；凭据要安全存储。
- **结论**：国内用户的实用选项，P3。

### 5.5 SFTP 到自有服务器——**次选（且是差异化卖点）**

- **做法**：选一台已保存主机（或新建），把加密包写到 `~/.jshell/sync.json`；直接复用现有 `ssh2` + SFTP 服务。
- **优点**：**零新依赖**；对 JShell 的目标用户（手里有服务器）最自然；数据完全私有；可放内网；无第三方账号。
- **缺点**：每台设备都要能连到那台「同步盘」服务器；离线不可用；要指定路径与权限。
- **安全**：SSH 传输已加密，再叠加同步包的 E2E，双重保险；登录凭据沿用现有 `safeStorage`。
- **结论**：可行，且有辨识度。

### 5.6 S3 兼容对象存储（OSS / COS / R2 / MinIO）

- **做法**：SigV4 签名 `PUT/GET`（`node:crypto` 可实现，不必引 SDK）。
- **优点**：便宜、可靠、跨平台；适合团队共享一个 bucket。
- **缺点**：配置项多（endpoint/bucket/AK/SK/region）；AK/SK 泄露风险高；国内厂商鉴权细节各异。
- **结论**：企业/进阶场景，P3 之后。

### 5.7 自建 JShell 云（账号）

- **优点**：体验最好（登录即同步、自动合并、设备管理、吊销）。
- **缺点**：后端服务、运维、账号安全、合规（隐私政策、等保）、成本；**并且直接打破「纯本地、无账号、不上报」的承诺**。
- **结论**：**现阶段不做**。将来若做，建议做成**可自托管**的独立服务，而不是强制云端。

### 5.8 CloudKit

- Apple 专属，需要开发者账号与 entitlement，Windows 不可用。
- **结论**：与跨平台目标冲突，排除。

### 5.9 手动导出 / 导入（现有能力）

- 现状：`exportConfig()` 只导出 `hosts + snippets`；`importConfig()` 会**重新生成 id** 且**不复制 `proxyJump`**。
- **结论**：作为 P0 的基线升级——补齐字段、可选加密、保留稳定 id 并修复 `proxyJump` 映射。

### 5.10 局域网直连 / 二维码

- **优点**：不经过任何云，最安全；适合「临时换机 / 一次性迁移」。
- **缺点**：需要同网段与配对；长期多设备不便。
- **结论**：作为「扫码迁移」补充功能，不做主线。

## 6. 安全设计（核心）

### 6.1 同步包格式（加密信封）

```json
{
  "format": "jshell-sync",
  "v": 1,
  "kdf": { "algo": "scrypt", "N": 131072, "r": 8, "p": 1, "salt": "<base64>" },
  "cipher": "aes-256-gcm",
  "iv": "<base64>",
  "tag": "<base64>",
  "ciphertext": "<base64>"
}
```

- **密钥派生**：`scrypt(口令, salt, N=131072, r=8, p=1) → 32B`（`node:crypto` 自带，无新依赖）。
- **对称加密**：`AES-256-GCM`，`AAD =` 规范化后的 header（防止攻击者把 KDF 参数改弱 / 换算法）。
- **口令策略**：≥ 12 字符，或提供「生成恢复码」；口令不落盘（若勾选「记住口令」则只存 `safeStorage`，并明确提示）。

**明文 payload 结构**：

```json
{
  "schema": 1,
  "exportedAt": "2026-10-27T03:00:00.000Z",
  "deviceId": "uuid",
  "rev": 42,
  "hosts": [],
  "snippets": [],
  "settings": {},
  "tunnels": [],
  "knownHosts": {},
  "secrets": {}
}
```

### 6.2 两层加密

| 层 | 保护对象 | 机制 |
| --- | --- | --- |
| 传输 / 共享 | 同步包整体 | 口令派生密钥 + AES-256-GCM（云盘不可读） |
| 本地落盘 | 密码 / 口令 | 本机 `safeStorage`（Keychain / DPAPI）重新封装 |

即使同步包被第三方拿走，没有口令也解不开；即使本机被翻，密码仍在系统密钥环保护下。

### 6.3 同步内容白名单

- **默认包含**：`hosts`、`snippets`、`settings`（仅跨设备有意义的子集）、`tunnels`、`groups`
- **默认不含**：`secrets`、`knownHosts`、`layout`、`window`、`logs`
- **可选开启**：`secrets`（强制设置同步口令）、`knownHosts`（弹窗提示「指纹是信任锚」风险）

### 6.4 威胁模型

| 威胁 | 缓解措施 |
| --- | --- |
| 云服务商 / 网盘读取内容 | E2E 加密，服务端只见密文 |
| 同步后端被入侵 / 篡改 | AEAD 认证，篡改即解密失败；`rev` 单调校验防回滚 |
| Token / WebDAV 口令泄露 | 仅存 `safeStorage`；不写日志；不进同步包 |
| 同步口令丢失 | 明确「不可恢复」；强制引导先导出备份；可选生成恢复码离线保存 |
| 设备丢失 | 在另一台设备改口令并覆盖 → 旧设备无法解密新包 |
| 误同步日志 / 终端内容 | 字段白名单，绝不整目录打包 |
| 私钥路径跨设备失效 | 记录 `~` 路径 + 设备内覆盖；缺失时显式提示而非静默失败 |

### 6.5 明确不做

- ❌ 不把 iCloud / 网盘的「自带加密」当作安全边界；
- ❌ 不在明文里放密码或私钥内容；
- ❌ 不把整个 `data/` 目录塞进网盘；
- ❌ 不把 token / 口令写进日志或 `localStorage`。

## 7. 冲突与合并策略

配置修改频率低、通常同一时刻只有一台设备在改，因此：

1. **稳定 id**：同步与导入都保留原 `id`（不要像现有 `importConfig` 那样重新生成）。
2. **删除用墓碑**：`deletedAt` 时间戳，否则「删掉的主机」会被另一台设备同步回来。
3. **字段级 LWW**：同 id 取 `updatedAt` 较新者；`settings` 按 key 各自 LWW。
4. **逻辑时钟**：`rev` 单调递增 + `deviceId`；若发现远端 `rev` 比本地已知的更小 → 判定为「旧备份 / 回滚」，**提示而不覆盖**。
5. **兜底**：无法自动合并时生成「冲突副本」，保留双方数据，绝不静默丢弃。

## 8. 跨设备细节

| 项 | 处理方式 |
| --- | --- |
| `privateKeyPath` | 存 `~/.ssh/id_ed25519` 这类可展开路径；导入后若不存在，主机标记为「需重新指定私钥」 |
| `localShell` / `hiddenLocalShells` | 设备相关，**不同步** |
| `sidebarWidth` / 窗口尺寸 / 布局 | 设备相关，**不同步** |
| `proxyJump` | 按主机 id 关联；同步 / 导入时必须保留 id 并做映射（现有导入的已知缺陷） |
| `knownHosts` | 默认不同步；开启后建议首次连接仍按 TOFU 复核一次 |

### 9.1 P0 实际交付（0.6.0）

```
src/shared/sync.ts              包格式、范围定义、落地方式类型、口令强度
src/main/services/sync-crypto.ts    scrypt + AES-256-GCM、KDF 参数校验、legacy 识别
src/main/services/sync-targets.ts   云盘目录探测（只读目录存在性，不联网）
src/main/services/sync-merge.ts     纯函数合并：稳定 id / LWW / 跳板机校验 / 指纹冲突
src/main/services/sync-service.ts   编排：导出、预览、导入（token 句柄）
src/renderer/src/components/SyncDialog.tsx  导出 / 导入双栏面板
```

关键边界，均有实现与测试兜底：

| 边界 | 实现方式 |
| --- | --- |
| 渲染层不能读写任意路径 | 只能传 `targetId`（来自探测结果的 id）或让用户在系统对话框里选；真实路径留在主进程 |
| 渲染层不能拿到已解密的包 | `inspect` 返回 `token` + 元信息 + 预览摘要，载荷缓存在主进程 |
| 含密码必须加密 | `plainBundle()` 直接拒绝带 `credentials` 的载荷；UI 也不给「不加密」选项 |
| 篡改与降级 | KDF 参数与 `meta` 进 AAD；离线爆破成本不能被文件自身削弱 |
| 恶意大参数 DoS | `N` 必须在 `[8192, 2^17]` 且为 2 的幂，`r/p/keylen` 有上限 |
| 替换导入的退路 | 导入前必然备份到 `data/backups/{import,replace}-<时间戳>/` |
| 设备私有字段 | `DEVICE_LOCAL_SETTINGS` 在导出与合并两侧都过滤 |

已覆盖测试（`tests/sync-*.test.mjs`）：加解密往返、错误口令、字节篡改、AAD 篡改、
KDF 降级、恶意 KDF、明文带凭据拒绝、legacy 解析、多云盘探测、目录白名单、
稳定 id 合并、跳板机断链降级、指纹冲突、替换模式分区语义。

### 9.2 覆盖前检测（0.6.1）

导入语义定为**远端覆盖本地**（`overwrite` 为默认），代价是不可逆，所以在写入前多了一道检测：

```
src/main/services/sync-diff.ts   纯函数：本地快照 × 同步包 → 变更清单
```

| 输出 | 含义 |
| --- | --- |
| `add` | 本机没有，将新增 |
| `update` | 同 id 已存在且内容不同，将被覆盖 |
| `update + localNewer` | **本机版本更新**，仍会被覆盖 —— 风险项 |
| `delete` | 仅替换模式：本机独有，将随替换消失 —— 风险项 |
| `same` | 无变化（只计数，不逐条列，避免淹没风险行） |

三道闸门：

1. **界面**：解读完立刻算差异，切换「覆盖 / 合并 / 替换」即时重算，风险行标红；
   无变更时「导入」按钮直接禁用并提示「本机已是最新」。
2. **主进程**：`sync:import` 自己再算一次，`risky > 0` 且 `acknowledge !== true` 就拒绝，
   渲染层被绕过也无法静默覆盖。
3. **备份**：确认后仍先备份 `data/backups/`，再应用。

覆盖模式的两条边界：

- **保留本机 `lastUsedAt`**：远端记录更新后，主机列表顺序仍按本机使用习惯。
- **指纹也照盖**，但会单独提示「N 个指纹已被同步包覆盖」——这是用户明确选择的结果，
  不是静默行为。

检测是纯函数、只吃两份快照，因此 P1 的文件夹自动同步会复用同一份报告，
不会出现「手动有检测、自动没有」的两套行为。

### 9.3 文件夹自动同步（0.7.0）

```
src/main/services/sync-transport.ts    read / write / watch 三件事
src/main/services/sync-bundle.ts       本机快照 → 同步包（手动/自动共用）
src/main/services/sync-auto-plan.ts    纯函数决策：跳过 / 记账 / 应用 / 暂停
src/main/services/auto-sync.ts         编排：去抖、防回声、暂停、状态上报
```

固定落点 `<目录>/JShell/jshell-auto.jshellsync`，与手动导出的日期文件名区分。

| 关注点 | 处理方式 |
| --- | --- |
| 本机改动 → 写回 | store 变更通知 + 1500ms 去抖 |
| 远端改动 → 拉取 | `fs.watch` 过滤文件名 + 800ms 去抖 |
| 自己写的文件又触发 watcher | 内容指纹比对，相等直接跳过（`decidePull = skip`） |
| 远端会覆盖本机较新改动 | 默认 `pauseOnRisky`，暂停并保留 `pending.report`；可一键覆盖或转手动 |
| 并发触发 | 单飞：执行中再次触发直接返回 idle，不排队堆积 |
| 写文件被打断 | 临时文件 + rename 原子写，云盘客户端读不到半个文件 |
| 启动时 | 拉一次（按配置方向），避免先推后拉把远端新内容盖掉 |
| 应用远端后界面 | 主进程推送状态 → 渲染层 store 更新 → 侧边栏/设置自动刷新 |
| 退出 | `before-quit` 停 watcher 与定时器 |

两种目录来源：

1. **探测到的云盘**（iCloud / OneDrive / Dropbox / Google Drive / 坚果云 / 百度网盘 / Nextcloud）；
2. **「选择文件夹…」**：系统对话框在主进程弹出，选中后写入配置——渲染层始终只传 `targetId`，
   无法用它读写任意路径。

口令用 `safeStorage` 封装存于 `data/sync.json`，不写进同步包、不经 IPC 回传。
没有口令时包为明文，此时不允许勾选「密码与私钥口令」。

### 9.4 SFTP 通道（0.8.0）

```
src/main/services/ssh-connect.ts      ConnectConfig 装配（含跳板机、只读指纹校验）
src/main/services/sftp-transport.ts   同一套 SyncTransport 的 SFTP 实现
```

自动同步的「同步位置」可以在**文件夹/云盘**与**SFTP 自有服务器**之间切换，上层逻辑完全不变。

| 关注点 | 处理方式 |
| --- | --- |
| 认证 | 复用已保存主机的密码 / 私钥 / ssh-agent，含 `proxyJump` |
| 路径 | 只接受绝对路径或 `~/`，相对路径直接拒绝；`~` 用 `realpath('.')` 展开 |
| 建目录 | SFTP 没有 `mkdir -p`，逐级 `stat` + `mkdir` |
| 原子写 | `.tmp` + rename；v3 rename 不能覆盖时先 unlink 再 rename |
| 变更检测 | 无 watch 接口，15 秒轮询 `mtime + size` 作为指纹 |
| 连接生命周期 | 一次同步共用一条连接，空闲 20 秒断开；切换配置时立即 dispose |
| 指纹 | **只读校验**：已知不一致即拒绝，绝不后台写入信任库 |
| 自检 | 「测试连接」建目录 + 写探针，错误原文回传 |

取舍说明：轮询最坏情况有 15 秒延迟，换来的是不需要在服务器上装任何东西、
也不依赖 `inotify` 转发。若将来要做「秒级」，可以再考虑 `inotifywait` 之类的可选增强。

### 9.5 WebDAV 通道（0.9.0）

```
src/main/services/webdav-transport.ts   第三个 SyncTransport 实现
```

| 关注点 | 处理方式 |
| --- | --- |
| 协议 | 仅 https；回环地址（localhost / 127.0.0.1）允许 http，便于自建与联调 |
| 地址 | 用户填「目录地址」，文件固定为 `<目录>/jshell-auto.jshellsync`；保存时规范化 |
| 存在性 | `HEAD`（405/501 时退化为 `GET` + `Range: bytes=0-0`） |
| 写 | `PUT`（WebDAV 天然整体覆盖，不需要临时文件） |
| 目录 | `MKCOL`，201 新建 / 405 已存在都视为成功 |
| 变更检测 | `ETag` + `Last-Modified` + `Content-Length` 组合指纹，15 秒轮询 |
| 错误 | 401 认证失败 / 403 无权限 / 507 空间不足 / 5xx 服务器错误，逐条翻译 |
| 密码 | 与同步包口令分开保存，`safeStorage` 封装，只回 `hasWebdavPassword` |
| 自检 | `MKCOL` → `PUT` 探针 → `DELETE`，一次验完连通性与权限 |

测试用 `node:http` 起了一个假 WebDAV（只在测试进程内监听回环端口），
覆盖读写往返、口令错误、自检与轮询触发，不依赖任何外部服务。

### 9.6 删除语义：不跨设备传播（0.9.2 决策）

**结论：删除只影响本机。** 在 A 机删掉一台主机，B 机不会跟着删；反过来，B 机下次推送还会把这条记录重新带回 A 机。

为什么不做墓碑：墓碑要为每条记录维护删除时间与「是否已被看见」，还要处理
「删了又加同名」「时钟不一致」「两台机同时删」这些边界。本工具的定位是**个人开发用的配置搬运**，
不是多端双向同步，这部分复杂度换不来收益。

由此带来的两个可预见行为，都是有意为之：

| 现象 | 解释 | 想要「让别处也删掉」怎么办 |
| --- | --- | --- |
| A 机删除后，B 机仍然有这台主机 | 同步只搬运存在的记录，不搬运「不存在」 | 在 B 机再同步一次，或直接用「替换本机」导入一份已删干净的包 |
| B 机同步后，A 机被删的主机又出现了 | B 机的配置里仍有这条，推送时自然带上 | 同上：先在本机删干净，再以「替换本机」为准 |

「替换本机」是唯一会删掉本机独有条目的模式，它按「包里有什么就是什么」执行，
因此可以当作「以某台设备为准」的补救手段——代价是本机独有的内容也会消失（有备份兜底）。

## 10. 对隐私说明的影响

`docs/privacy.md` 已同步新增「配置同步（可选）」一节，明确：

- 默认**不导出**；只有用户主动点「生成同步包」时才会写文件；
- 只写用户指定的那一个文件，**不访问**任何云服务 API、不后台自动上传；
- 写入内容由勾选范围决定，默认不含密码、不含主机指纹、不含布局与日志；
- 同步口令不保存、不上传；忘记口令等于文件不可恢复；
- 文件本身归用户所有，删除即彻底移除（应用不保留副本）。

```

           [ ] 主机指纹（默认关：信任应由设备自己决定）

加密保护   (•) 口令加密（推荐）  ( ) 不加密（含密码时禁用）
           [口令] [再输一次]   强度提示
[ 生成同步包 ]   方式：云盘目录 · 已加密

```
